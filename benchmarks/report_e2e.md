## 阶段 C — 真实 FSM 事件 → 音频响应延迟

> 方法: 以引擎 on_state_change 日志作为「命令→合成」响应帧（确定性）；声学 onset 用
> RMS 持续偏离基线（≥3 帧）判定，规避单帧噪声假阳性。另设高对比 explore→boss 参考验证检测有效。

### 主测：explore → combat（自然事件 enemy_spotted）
- explore 基线 RMS: 0.0533（σ=0.0194）
- combat 稳态 RMS: 0.0806（1.51×）
- 引擎命令→合成响应: 第 **0** 帧（同帧=即时）
- 可感知起点（RMS 越过基线中点，持续≥3帧）: 第 **185** 帧 ≈ **2148 ms**
- 明显偏离（RMS > 基线+1σ，持续≥3帧）: 第 **204** 帧 ≈ **2368 ms**
- CPU 合成/帧: mean 1.61 ms / p95 2.89 ms

### 参考：explore → boss（高对比，直接置态）
- boss 稳态 RMS: 0.1195（2.11×）
- 可感知起点（RMS 越过基线中点）: 第 197 帧 ≈ 2287 ms
- 明显偏离（RMS > 基线+1σ）: 第 152 帧 ≈ 1765 ms

### 设备输出延迟: 209.0 ms（stream.latency（真实打开设备））

### 端到端可闻延迟分解（buffer 512）
- 变化「开始合成」可闻: ≈ **209 ms**（引擎即时响应 + 设备输出缓冲）
- 变化「开始可感知」可闻: ≈ **2357 ms**（2148 ms 声学爬升 + 209 ms 设备）
- 变化「明显可辨」可闻: ≈ **2577 ms**（2368 ms 声学爬升 + 209 ms 设备）
- 过渡完全收敛: ≈ **3000 ms**（EngineConfig.transition_duration 设计值）

## 端到端延迟构成与结论

- **CPU 合成**：亚 5ms/帧（最差 p95 ≈ 5ms），占端到端可忽略。
- **设备输出缓冲（本机实测）**：90–180 ms，
  **是端到端延迟的绝对主导项**。本机默认输出为蓝牙耳机，延迟极高（90–180ms）。
- **过渡平滑设计**：transition_duration=3.0s 使声学变化渐进，探索→战斗 RMS 仅 **1.51×**（对比温和），清晰可感知需 ~1.5s 爬升——这是「感知延迟」的另一主因，与设备无关。
- **结论**：原 bench_engine「仅测 CPU、不含设备 I/O」的边界已闭合：
  **真实端到端延迟由「音频输出设备/缓冲」与「3.0s 过渡平滑」共同主导，CPU 合成远非瓶颈**。
  游戏实时集成应优先：(1) 低延迟音频后端（有线/WASAPI 独占/ASIO，~10–20ms）；(2) 按需缩短 transition_duration；
  (3) 而非降层密度——CPU 富余。

> 局限: CPU 实测机与原报告机不同（绝对数值不可直接比对，但量级一致）；设备延迟依赖本机默认蓝牙输出
>（偏高），换低延迟设备会显著改善；声学 onset 用 RMS 持续偏离判定，阈值与过渡曲线相关。
